# V2 Bounded Progression Voicing Optimizer Contract

Status: reviewed implementation handoff for `V2/spec`
(`jcpe-milestone-advanced-craft-ulj.1.1`). This document, the public module
`src/theory/progression-optimizer-contract.ts`, the fixtures under
`tests/fixtures/progression-optimizer/`, and the independent validator
`scripts/validate-v2-contract.ts` are the complete authority for the future
`V2/build` production package. The production optimizer does not exist yet;
nothing in this package was generated by it.

Pinned identities:

- contract schema `changes.theory.progression-optimizer-contract.v1`
- engine `changes.progression-optimizer` version 1
  (tag `changes.progression-optimizer.v1`)
- cost policy `changes.progression-optimizer.aggregate-cost` version 1
- search policy `changes.progression-optimizer.bounded-beam` version 1
- tie-break policy `changes.progression-optimizer.tie-break` version 1

## 1. Ownership and layer boundary

V2 lives in the `theory` layer. The contract module imports only `domain`
types plus the theory-internal `voicing-candidates-contract`,
`voice-assignment-contract`, and `syntax-contract` modules. The production
package must obey the same boundary: no content, UI, audio, persistence,
export, playback, or application-state import, no wall-clock read, no
randomness, no `Date`, no timers.

V2 consumes:

- **V0 retained candidates** — at most `MAX_VOICING_RETAINED_CANDIDATES = 24`
  per event, presented as V1 `UnassignedVoiceFrame` values. V2 never inspects
  or re-derives V0 generation internals and never reorders, edits, or
  re-scores a frame.
- **V1 transition facts** — through an injected `VoiceAssignmentOperations`
  oracle. Every pairwise cost, motion, lock, and refusal fact comes from
  `assignVoiceTransition`. V2 memoizes oracle outcomes per
  `(windowOrdinal, layerOrdinal, fromCandidateId, toCandidateId)` and never
  re-derives or edits any motion fact. Frame-internal validation (voice
  ordering, pitch/midi agreement, role context) is V1's job; V2 validates
  only the V2-level structure listed in Section 4.

  *Content-memoization law (amendment #1, 2026-07-23).* The V1 contract
  fixes cost and refusal facts as functions of musical content alone: the
  two frames' voices and role contexts plus the forwarded locks — never
  event ids or request ids. Production may therefore additionally memoize
  oracle outcomes by that full musical content, which is observationally
  invisible against any V1-conforming oracle and lets repeated chord
  shapes across a chart share one real evaluation. Test oracles must be
  content-deterministic: identical content must yield identical cost and
  refusal facts (every reviewed fixture already satisfies this; a table
  oracle keyed by event ordinal is conforming only when its frames differ
  in content wherever its costs differ).

Downstream consumers (G4 constraint workbench, E1 MIDI export, U6
voice-leading workbench) depend on this public contract, not on optimizer
internals.

## 2. The aggregate cost vector and total order

`PROGRESSION_COST_AXES` freezes seven axes, exactly the V1 reported cost
axes, in the plan Section 12.5 order:

| Axis | Aggregation | Cap (from V1 per-transition caps × 8,192 transitions) |
|---|---|---|
| `totalAbsoluteMotion` | sum | 8,192 × 889 = 7,282,688 |
| `maximumAbsoluteLeap` | max | 127 |
| `commonTonesLost` | sum | 8,192 × 7 = 57,344 |
| `crowdedLowIntervals` | sum | 8,192 × 6 = 49,152 |
| `doubledGuideTones` | sum | 8,192 × 6 = 49,152 |
| `omittedColors` | sum | 8,192 × 16 = 131,072 |
| `totalSpan` | max | 127 |

A chain's aggregate cost folds its transitions' V1 `VoiceAssignmentCost`
values: sum axes add, max axes keep the largest value. A chain with zero
transitions (single-event segment) has the all-zero vector. Cost axes are
never weighted, normalized, or summed across axes; the unit of each axis is
the V1 unit unchanged.

**Dominance.** Chain A weakly dominates chain B when A ≤ B on every axis and
A < B on at least one. Equal vectors do not dominate each other.

**Total order (`PROGRESSION_TIE_BREAK_ORDER`).**
1. `aggregate-cost-axis-order`: lexicographic comparison over the seven axes
   in the frozen array order, smaller first.
2. `candidate-id-sequence-lexicographic`: the chain's candidate-id sequence
   (earlier events first; `candidate-000` < `candidate-001` in UTF-16 order).
   Distinct chains over the same span always differ here, so the order is
   total and byte-stable.

## 3. Request shape

`ProgressionOptimizationRequest` carries:

- `identity`: request id (`^[A-Za-z0-9._-]{1,128}$`), `documentId`,
  `sourceRevision` (non-negative integer), and the exact engine/cost/search/
  tie-break pins above. Any pin mismatch refuses `progression.policy_invalid`.
- `loopClosure`: boolean (Section 7).
- `maxWorkQuanta`: integer in `1..8192`.
- `events`: 1..8,192 `ProgressionEvent` records in chart order.

Event kinds:

- `auto`: 1..24 candidate frames, ordered by `roles.candidateId` ascending,
  duplicate-free, every frame naming the event's `eventId`.
- `fixed` (`reason` `manual` or `frozen`): exactly one immutable candidate
  frame. The optimizer never rewrites its pitches under any circumstance.

Each event carries `chainBoundary` (`continue` | `reset`; the first event's
value must be `reset`) and a `ProgressionEventConstraints` record:

- `families`: null or a non-empty duplicate-free subset of
  `AUTO_VOICING_FAMILIES` in that array's order;
- `range` and `bassRange`: null or inclusive MIDI bounds with
  `lowMidi <= highMidi`, each within 0..127;
- `locks`: 0..7 V1 `VoiceLock` records forwarded verbatim to every V1
  transition targeting this event; V2 never interprets lock pitches itself.

## 4. Request validation and refusal precedence

Validation walks `PROGRESSION_VALIDATION_PRECEDENCE.order`; the first
failing check wins. Per-event checks run in event order; inside one event,
`event_invalid` (kind/eventId/chainBoundary structure), then
`candidate_invalid` (count, ordering, duplicates, eventId agreement), then
`constraint_invalid` (families/range/bassRange/locks structure). All
refusals are typed `PathRefusal`s with `partialResult: false` and a JSON
pointer to the offending field. Refusal codes are frozen in
`PROGRESSION_REFUSAL_CODES`.

Resume-time refusals: advancing or cancelling a `terminal` state refuses
`progression.resume_invalid`; advancing a state whose identity or
continuation tag no longer matches the module constants refuses
`progression.resume_stale`. Staleness of the *document* (edits after
`sourceRevision`) is detected by the application runner, which cancels with
reason `stale-revision`; V2 itself never reads the document.

## 5. Segmentation, windows, and boundary conditions

- **Segments.** `chainBoundary: "reset"` starts a new segment. Segments are
  optimized independently; no transition cost crosses a reset.
- **Windows.** Each segment splits into consecutive windows of at most
  `MAX_PROGRESSION_WINDOW_EVENTS = 512` events. A segment with more than 512
  events is optimized window-by-window with **fixed boundary voicings**: the
  selected candidate of the previous window's last event becomes the sole
  seed (`boundaryCondition: "fixed-start"`) of the next window, whose first
  layer is that single carried state with the zero cost vector. A
  fixed-start window's realizations cover only the window's own events —
  the carried boundary candidate is not repeated in `eventIds` /
  `candidateIds` — but the boundary transition's cost folds into the
  window's chains. Every multi-window segment emits one degradation record
  (`reason: "window-partition"`; its `eventIds` list the first event id of
  every window after the first), and the whole outcome's termination
  becomes `exhausted`.
- Windows and segments are optimized in request order, strictly
  sequentially; a window begins only after the previous window's selection
  is final.

## 6. The bounded beam search

Per window, layer `k` holds states for event `k` of the window. Frozen
semantics:

1. **Seeding.** Layer 0 states come from the first event's candidates that
   survive constraint filtering (Section 6.1), one state per candidate with
   the zero cost vector, in candidate-id order — except a `fixed-start`
   window, which seeds exactly the carried boundary state. Each seeded state
   consumes one work unit and counts `seededStates`.
2. **Expansion.** For each layer transition, frontier states are visited in
   the frozen total order (Section 2); for each state, target candidates
   (survivors of constraint filtering, candidate-id order) are attempted in
   order. Each `(state, targetCandidate)` attempt consumes one work unit and
   counts `statePairExpansions`. The V1 oracle is invoked once per distinct
   `(window, layer, fromCandidateId, toCandidateId)` and memoized
   (`oracleTransitionCalls`); a refused pair (`no-assignment`) counts
   `oracleRefusedTransitions` once per distinct pair, and every attempt
   whose memoized outcome is a refusal generates no state. A successful
   attempt creates a state (`generatedStates`) whose cost folds the
   transition's V1 reported axes into the parent's aggregate.
3. **Dominance pruning.** After a layer's generation completes, states are
   grouped into buckets. The bucket key is the target candidate id — except
   when loop closure will apply to this window (Section 7), where the key is
   the pair (chain's first-event candidate id, target candidate id): closure
   cost depends on the chain's first candidate, so chains with different
   first candidates are never comparable before closure. Within one bucket
   only, weakly dominated states are discarded (`dominancePrunes`).
   Equal-cost states are all retained. Cross-bucket dominance is never
   applied (different candidates have different futures).
4. **Beam retention.** If the union of bucket survivors exceeds
   `PROGRESSION_BEAM_WIDTH = 48`, sort by the frozen total order, keep the
   first 48, and count the rest as `beamEvictions`. Any eviction anywhere in
   the command makes the final termination `exhausted` and emits one
   degradation record per affected window (`reason: "beam-eviction"`, its
   `eventIds` listing, in chart order, the event ids of the layers where
   evictions occurred in that window).
5. **Quantum discipline.** Work units are consumed in exactly the order
   above. `advance` consumes at most `PROGRESSION_WORK_QUANTUM_UNITS = 1152`
   units and increments `workQuanta` by exactly one even when the search
   finishes mid-quantum. A quantum boundary may fall anywhere, including
   mid-layer; scheduling never changes any observable value
   (Section 9, yield-schedule equivalence). If `maxWorkQuanta` is consumed
   and the search is unfinished, the outcome is `unfinished` /
   `work-quanta-cap` with stats and no partial option set.

### 6.1 Constraint filtering

Before seeding or targeting an event, its candidates are filtered by
`PROGRESSION_CONSTRAINT_FILTER_ORDER`: `families` (frame's
`roles`-declared family must be in the subset), then `range` (every voice
MIDI within bounds), then `bassRange` (ordinal-0 voice MIDI within bounds).
A candidate failing several filters is charged once, to the first failing
kind (`constraintFilteredCandidates`). **Fixed events are never filtered**:
a fixed candidate that violates a constraint is preserved bit-for-bit and
reported once per event as a degradation
(`reason: "fixed-candidate-constraint-conflict"`, `constraintRefs` naming
each violated constraint); termination is unaffected.

The family of an auto candidate frame is determined by its
`roles.sourceId`/template identity as published by V0; the fixture
representation names it directly, and the production ingest must derive it
from the same V0 fact, never by re-classifying pitches.

### 6.2 Dead layers and conflicts

If an auto event's surviving candidate set is empty, or a layer generates
zero states (every pair refused), the segment has no full-length
realization. The whole command returns `no-realization` (termination
`complete` or `exhausted` per the rules above) carrying one
`ProgressionConflict` per failing segment: the first failing event's id,
`constraintRefs` naming the responsible constraints —
filter kinds that emptied the set (sorted by the frozen filter order), lock
refs when the oracle refused with lock reasons, or
`transition-no-assignment` with `voiceId: null` otherwise —
`minimality: "bounded-small"`, and empty `explicitRelaxations` (no
relaxation is ever authorized). Constraint refs are ordered by
`PROGRESSION_CONSTRAINT_FILTER_ORDER` kind first, then lock refs by
ascending `voiceId`, then `loop-closure`, then `transition-no-assignment`,
each distinct ref listed once. Other segments' partial successes are
discarded; the command is atomic.

## 7. Loop closure

`loopClosure: true` requests last-to-first transition cost. It applies only
when the request is a single segment in a single window; otherwise it is
skipped with one degradation record (`reason: "loop-closure-skipped"`).
When it applies: after the final layer's retention, for each surviving
chain in the frozen total order, invoke the oracle from the chain's last
frame to the chain's own first-event candidate — memoized in a dedicated
`loop` namespace per `(fromCandidateId, toCandidateId)`, distinct from the
layer memo space; each attempt consumes one work unit
(`loopClosureUnits`). A refused closure drops the chain
(`loopClosureRefusals`). If every chain drops, the outcome is
`no-realization` with a conflict ref of kind `loop-closure` on the first
event. Closure costs fold into the chain aggregate before Pareto selection,
and surviving realizations set `loopClosureApplied: true`.

## 8. Outcomes

- `optimized`: per segment-window, a `ProgressionSegmentOutcome` whose
  `realizations` list the final layer's non-dominated chains (weak
  dominance, now across all surviving chains) sorted by the frozen total
  order, `realizationOrdinal` 0.. in that order, at most
  `MAX_PROGRESSION_ALTERNATIVES = 48`; index 0 is the selected realization.
  `aggregateSelectedCost` folds every selected chain's cost across segments
  and windows (sum axes add, max axes keep the maximum).
- `no-realization`: conflicts as in Section 6.2; never partial.
- `unfinished` (`work-quanta-cap`) and `cancelled`: stats and diagnostics
  only; no partial option set, mirroring the plan's cancellation law.
- Every outcome carries `ProgressionSearchStats` (all fourteen work
  counters, all four memory counters) and the frozen `ProgressionExplanation`
  literals (`wallTimeAffectedSelection: false`, `documentMutated: false`,
  `hardConstraintsRelaxed: false`, `manualFrozenPitchesRewritten: false`,
  `deterministicForIdenticalInputs: true`).

Work-unit accounting must satisfy the frozen identity
`workUnits = seededStates + statePairExpansions + loopClosureUnits` and
every counter must respect `PROGRESSION_WORK_LIMITS` /
`PROGRESSION_MEMORY_LIMITS`; a would-be overflow refuses
`limit.progression_work_exceeded` naming the counter, observed value, and
limit. With correctly derived requests these ceilings are unreachable; the
refusal is a failsafe, not a planning device.

## 9. Stepper state machine

| From | Operation | To | Notes |
|---|---|---|---|
| — | `initialize` (valid request) | `running`, `quantaConsumed = 0` | validates, seeds nothing, consumes no quanta |
| — | `initialize` (invalid request) | refusal | Section 4 precedence |
| `running` | `advance` | `running` | one quantum consumed, search unfinished, budget remains |
| `running` | `advance` | `terminal` | outcome `optimized` / `no-realization`, or `unfinished` when the consumed quantum exhausts `maxWorkQuanta` |
| `running` | `cancel(reason)` | `terminal` | outcome `cancelled`, reason `user-cancel` or `stale-revision` |
| `terminal` | `advance` / `cancel` | refusal | `progression.resume_invalid` |
| any | `advance` with mismatched pins/tag | refusal | `progression.resume_stale` |

Laws:

- **Determinism.** Identical request, identical deterministic oracle, and
  identical operation sequence produce byte-identical states at every step.
- **Yield-schedule equivalence.** For any two advance schedules that reach a
  terminal state, terminal outcomes (including stats and realization
  ordering) are byte-identical. Quantum boundaries are invisible in every
  observable.
- **Purity.** States are immutable values; `advance` never mutates its
  input; the request (and the document behind it) is never modified.
- **No semantic clocks.** 100 ms (64-event interactive target) and 500 ms
  (large-chart ceiling) are release performance gates measured over this
  contract's operations; they never select, truncate, or reorder output.

## 11. Independent proof contract

The fixture package under `tests/fixtures/progression-optimizer/` is the
independent authority. Its cases were authored against this document alone,
before any production optimizer existed, with hand-computed expectations;
`scripts/validate-v2-contract.ts` recomputes every expectation with its own
reference implementations (an exhaustive chain enumerator for brute-force
certified cases, plus a reference beam stepper implementing Sections 5–8
verbatim) and rejects any divergence. The validator imports nothing from
`src/`.

Fixture families and the laws they witness:

- `optimization-cases.json` — positive small cases (brute-force certified:
  reference beam must equal exhaustive enumeration), Pareto-front content
  and ordering, tie-breaks, dominance-prune and counter accounting, refusal
  near-misses for every code in Section 4's precedence order.
- `boundary-cases.json` — fixed manual/frozen seams (exact pitch survival,
  constraint-violating fixed candidates preserved plus degradation), reset
  segmentation, loop closure (applied, refused, skipped), impossible
  locks/ranges yielding `no-realization` with named constraints.
- `limit-cases.json` — the 24/48/512/8,192 edges: 24-candidate events, beam
  eviction at width 48 with `exhausted` termination, generator-descriptor
  cases for the 512-event window partition with fixed boundary voicings and
  the 513th-event degradation, the 8,193-event refusal, and quantum-budget
  exhaustion (`work-quanta-cap`).
- `stepper-cases.json` — the Section 9 matrix: quantum-by-quantum counter
  trajectories, yield-schedule equivalence, cancellation at fixed quantum
  indices, terminal-state resume refusals, stale-pin refusals.
- `mutation-controls.json` — JSON-pointer corruptions of expectations and
  laws that the validator must catch, each naming its expected finding code.
- `trace-ledger.json` — reciprocal traces: every parent invariant and
  success criterion of the V2 bead maps to named case ids and mutation
  controls; every case and control belongs to a trace; every evidence owner
  is a named future test file for `V2/build`.
- `provenance-ledger.json` — authority classes for every judgment-bearing
  number: plan-frozen values (`reviewed-contract`), arithmetic products
  (`mechanical-derivation`), and the V0/V1 restatements, with
  `expectedValuesGenerated: false` and `productionOutputUsed: false`.

Transition costs in fixtures are literal per-pair tables standing in for the
injected V1 oracle. This is deliberate: V2's laws quantify over any
deterministic oracle, and table oracles keep the spec fixtures independent
of V1 numerics. `V2/build` must additionally run the named integration tests
against the real `assignVoiceTransition`.

## 12. Implementation handoff and forbidden shortcuts

The following are contract violations even if a demo appears to work:

- Calling the V0 generator or V1 oracle outside the memoized discipline, or
  re-deriving/adjusting any motion, cost, or lock fact inside V2.
- Rewriting, transposing, re-spelling, or re-scoring a Manual/Frozen
  candidate, or "helpfully" dropping a constraint the fixed candidate
  violates instead of preserving both and degrading visibly.
- Any hidden relaxation: weighting axes, normalizing units, comparing across
  axes without the frozen lexicographic order, dropping equal-cost states,
  or cross-bucket dominance pruning before the final layer.
- Wall-clock, load, `Math.random`, iteration-order, or `Map`-insertion
  nondeterminism anywhere in selection; any quantum-schedule-visible
  observable.
- Returning partial realizations from `unfinished` or `cancelled` outcomes,
  or promoting `exhausted` to `complete` when any eviction or window
  partition occurred.
- Silently truncating events, candidates, alternatives, or counters instead
  of the typed refusal/degradation named here.
- Generating fixture expectations from the production optimizer, or letting
  the production module import fixture or validator code.

Handoff note: `V2/build` implements `ProgressionOptimizerOperations` in
`src/theory/` (suggested module `progression-optimizer.ts`), satisfies every
fixture family via the named future test files in the trace ledger, adds
integration coverage against real V0 candidates and the real V1 oracle, and
records the 100 ms / 500 ms performance observations without letting either
clock touch semantics. No production shortcut or feature reduction is
authorized by anything in this document.
